# Screen Off — Agent Working Agreement

> Screen Off is a lightweight menu bar utility that keeps a Mac online while automatically lowering the built-in display and keyboard backlight. This file holds only high-frequency constraints; development, capability, and release details live in `Docs/`.

## Stack and Product Boundaries

- Swift 6, SwiftUI, AppKit, IOKit; the project is generated by XcodeGen and supports macOS 14 and later.
- The first version supports only the built-in display and keyboard of Apple Silicon MacBooks.
- Menu bar resident app with no Dock icon; Settings uses a standalone `Settings` scene.
- The first version ships with Developer ID signing and notarization for direct distribution; the Mac App Store is not a target.
- Never present an uncertain or unverified system capability as done; state its status explicitly in the docs and the UI.

## Coding Rules

- Do not multiply entities beyond necessity; no GPUI, Tauri, Electron, or cross-platform abstractions.
- Reply in Chinese, keep it brief, use emoji when helpful.
- App-level state is centralized; user preferences use `UserDefaults`, system capabilities live in separate services.
- Any change to brightness, power, or lid state must save the original state first and restore it when the feature is turned off, on quit, and on recovery from an abnormal exit.
- Private frameworks must be resolved dynamically with capability probing and graceful degradation; a missing symbol must never crash the app.
- Keep-awake-with-lid-closed uses a separate `PreventSystemSleep` assertion, held and released independently of the plain idle assertion, and falls back immediately when unplugged.
- Never store input content, screen content, remote session information, or any credentials.
- For UI rewrites, re-layouts, new entry points, or visual structure changes: describe the structure in 3–4 bullets and wait for confirmation before writing code.
- Code changes that affect architecture, features, distribution, permissions, or safety boundaries must update the relevant guide in `Docs/` in the same change.
- Avoid unnecessary Xcode builds; build after completing a verifiable stage.

## Workflow

- Before a large change (more than 5 files or spanning multiple system boundaries), list 3 invariants and wait for confirmation.
- Use `./Script/build_and_run.sh` as the single run entry point.
- System capabilities must be verified on a real MacBook; compiling is not feature completion.
- Lid, power, and brightness tests must not leave system state behind; check and restore defaults after verification.

## Documentation

- Documentation, including `Docs/`, is written in English; only the README has a Chinese counterpart (`README.zh-CN.md`).
- `Docs/README.md` is the documentation entry point. Keep public documentation focused on development, capability boundaries, and releases.
- Keep task plans, todos, and historical working notes outside the repository; do not recreate separate tracking folders.
- Preserve unverified capabilities and outstanding hardware checks in `Docs/system-capabilities.md` or `Docs/releasing.md`.
